# Podcast Toolkit 專案優化計劃

日期：2026-09-05
檢視分支：`vs/subtitle-polish-flow`
比較基準：`origin/main`，兩者目前皆為 `061a3e9`
檢視範圍：字幕潤飾、儲存與集數狀態、背景轉錄、測試、Python 相容性、macOS 打包與文件。

## 結論先行

目前不建議直接把這個分支當成可發布版本。新增的字幕潤飾流程已經能運作，但仍有幾個會改錯字幕或回報錯誤完成的風險；同時，HTTP 409 的處理只覆蓋共用儲存流程，尚未解決全域集數狀態造成的多分頁資料誤寫。

建議依序處理：

1. 先修正字幕輸出驗證、時間切分、講者對應與備份安全。
2. 再處理集數識別、HTTP 409、背景工作隔離，避免寫入錯集。
3. 接著固定 Python 執行環境與 macOS 打包來源，讓另一台電腦可重現。
4. 最後拆分前端與後端大檔案，並補上真正能驗證瀏覽器行為的測試。

## 主要問題與優先級

### P0：字幕品質與資料正確性

#### 1. 成功摘要覆蓋既有警告

位置：`podcast_toolkit/web/transcribe_job.py` 的 Breeze 收尾流程。

校對或斷句重整失敗時會先寫入 `note`，字幕潤飾成功後又用同一欄位寫入摘要，導致使用者看不到先前的警告；正常成功時也會固定產生 `note`，破壞原本「只有跳過或警告才顯示提示」的語意。

處理方式：把 `summary` 與 `warnings` 分開保存，前端分別顯示；保留每個失敗步驟，不讓後續步驟清掉前面訊息。

#### 2. 驗證失敗仍可能寫入字幕，工作仍回報完成

位置：`podcast_toolkit/subtitle_polish.py` 的 `run()`，以及 `transcribe_job.py` 的收尾流程。

目前會先把修改後的 SRT 寫回，再把驗證結果放入報告；即使報告有格式錯誤、重疊或非正向時長，背景工作仍可能以 `done` 結束。

處理方式：先在記憶體內驗證候選輸出，驗證不通過就保留原檔、不寫 speakers sidecar，並回報可定位的錯誤；工作狀態必須反映潤飾失敗或需要人工檢查。

#### 3. 超長字幕只切一次

目前一張過長卡只被拆成兩張。當原卡很長時，兩張仍可能超過字數或停留時間上限，而 `ok` 只檢查錯誤數，沒有檢查殘留的品質違規。

處理方式：使用有最大深度的遞迴或迭代切分；每次切分後重新檢查，直到符合規則或標記為未解決。報告列出卡號、原因與建議人工處理項目。

#### 4. 切分沒有真正使用逐字時間

`_split_long_card()` 接收 `words` 後未使用，切點仍採文字長度比例。這會讓字幕卡邊界可能落在實際發音之前或之後，無法達成使用逐字時間調整字幕的目的。

處理方式：文字能對上逐字資料時，切點只能落在逐字邊界；無法對上時才使用既有時間分配工具作降級處理，並在報告標記為估算切分。

#### 5. 自動合併可能跨越不同講者

目前為了處理接續詞，強制前綴規則可繞過講者相同檢查；「事情」與「概念」也不適合作為無條件接尾規則。這會把下一位講者的文字併回前一張，造成字幕與鏡頭切換對應錯誤。

處理方式：已知講者不同時禁止自動合併；只有同講者或沒有講者資料的單軌情況才可合併。跨講者但疑似詞中硬切的案例列為人工檢查。

#### 6. 閃字幕合併規則沒有處理第一張卡與重疊

目前主要只向前找鄰居，第一張短卡無法向後尋找；間隔判斷也允許負值，可能把重疊卡當成可合併對象。

處理方式：同時評估前後鄰居，要求正常合併的間隔為 `0 <= gap <= 門檻`，並把真正重疊交給獨立的重疊處理規則。合併前一併檢查講者、標點與逐字時間。

#### 7. 斷句位置可能留下懸空連接詞

目前切分候選使用獨立正規表示式，可能把「或是」等語意單位拆在不自然的位置；專案已有 `subtitle_cleanup` 與 `word_break` 的語意邊界規則，卻未共用。

處理方式：統一使用既有斷句與詞界規則，新增的潤飾流程只負責排序與編排，不再建立第二套互相衝突的斷句定義。

### P1：儲存、集數與背景工作的可靠性

#### 8. HTTP 409 修復不完整

共用 `postSave()` 已處理 409 後重新開集再重試，但字幕時間偏移的儲存路徑仍直接呼叫 `/api/save`，因此同一類狀態遺失仍可能失敗。

處理方式：所有會寫入編輯狀態的路徑統一經過單一儲存服務；補測 409 後重新開集、重新開集失敗、重試失敗與沒有快取集數等情境。

#### 9. 全域目前集數會造成多分頁誤寫

後端以單一 `holder["ep"]` 保存目前集數，`/api/save` 依當下全域值寫檔。分頁甲開集 A、分頁乙開集 B 後，分頁甲送出的資料可能得到 200，卻被寫進集 B；現有前端只處理「目前集數不存在」，無法辨識「目前集數已被另一分頁換掉」。

處理方式：每個集數相關請求帶穩定的集數識別與版本號；後端檢查請求識別是否與目標一致，不一致回 `409` 或 `412`，絕不靜默寫入另一集。長期可改成集數明確放在網址或請求標頭，逐步移除全域目前集數作為寫入依據。

#### 10. 背景工作沒有集數識別

轉錄狀態目前是模組層級單一工作，狀態資料沒有 `episode_id` 或 `job_id`。使用者在工作進行中切換集數時，新集數的前端可能讀到舊集數的進度或完成結果；雖然部分 worker 捕捉了原始 `Episode`，前端顯示仍缺乏隔離。

處理方式：工作狀態加入 `job_id`、`episode_id`、`started_at` 與輸出路徑；前端只接受目前集數與目前工作相符的狀態。切換集數時顯示原集數仍在背景處理，或在工作期間禁止切換並提供明確取消流程。

#### 11. SRT 與 speakers sidecar 不是同一個寫入交易

潤飾流程先原子寫 SRT，再另寫 speakers；第二步失敗時，卡號已更新但講者映射仍是舊版本。

處理方式：先產生兩個暫存檔並驗證卡號集合一致，再以可回復的方式替換；任一步失敗就由同一批備份還原。這個共用寫入工具也應供 Breeze 匯入與 reflow 使用。

#### 12. 備份檔名固定，重跑會覆蓋上一份備份

字幕潤飾使用固定的 `.pre-polish.bak` 檔名，第二次執行會覆蓋第一次的原始狀態。

處理方式：採用含日期時間與工作識別的備份檔名，報告保存實際備份路徑；另訂保留數量或清理政策，避免集資料夾無限增長。

### P1：Python 與發布流程

#### 13. Python 版本宣告與實際相容性不一致

短期方案：把支援範圍收斂到已驗證的 Python 3.9 至 3.12。
長期方案：以 `numpy` 取代 `audioop` 的波形峰值計算，或只在 3.13 以上安裝相容套件，並把 CI 擴充到實際支援的版本。

建議採長期方案，因為專案本身已有 `numpy`；但必須補上音訊峰值、空音訊、負值取樣與不同取樣寬度的測試。

#### 14. 打包無法只靠 Git 重現

Breeze sidecar 約 3.7GB，現在依賴本機 `~/.podcast-toolkit/breeze-stage/`，另一台電腦從 Git 下載後不能直接重建相同 App。

處理方式：建立 sidecar 版本清單與雜湊、下載或匯入腳本、建置前檢查，以及不含大型模型的快速打包檢查。大型模型不放進 Git，改用明確版本化的發布資產或內部儲存位置。

#### 15. 脫離 Git 的檔案可能被打進 App

`build_app.sh` 的髒工作樹判斷只看 `git diff`，不會把未追蹤檔案算進去。目前新增的 `subtitle_polish.py` 未追蹤時，App 可能含有 Git 版本號中不存在的程式碼。

處理方式：發布建置改用 `git status --porcelain --untracked-files=normal` 判斷；預設拒絕髒工作樹發布，或在版本識別中明確加上髒狀態。建置同時產生來源清單與檔案雜湊。

#### 16. 版本號與安裝文件分散

`pyproject.toml` 與 `setup_app.py` 的版本號不同；README 仍描述已移除的 `install.sh` 流程，也沒有記錄新增的字幕潤飾階段。

處理方式：建立單一版本來源，讓 Python 套件、App、DMG 與 `/api/version` 共用；同步修正安裝步驟、Breeze 流程、模型資產需求與另一台電腦的開發說明。

### P2：可維護性與測試

#### 17. 前端單檔過大，且目前前端測試多為文字比對

`app.js` 約 8,433 行、`app.css` 約 3,829 行；現有前端冒煙測試主要檢查原始碼字串，無法驗證 409 重試、多分頁、非同步競態與實際畫面狀態。

處理方式：先抽出 API／儲存復原、集數識別、轉錄輪詢與編輯狀態四個邊界，再逐步移動功能；每次抽出都保持行為不變。新增 Node 測試或 Playwright，至少覆蓋關鍵請求序列。

#### 18. 字幕規則與設定重複

潤飾模組自行定義長度、反應詞與時間門檻，與 `defaults.yaml`、`resegment`、`reflow`、`seg_check` 的規則可能分歧。

處理方式：建立單一字幕品質設定物件，由設定檔載入；分析器、修復器與報告都使用同一套門檻，並保留每集覆寫能力。

#### 19. 驗證報告資訊不足

目前只回傳總數，傳統字檢查也過於狹窄，無法讓使用者快速定位哪一張卡需要人工處理。

處理方式：報告增加卡號、時間、原文、修改後文字、規則名稱與是否採用估算時間；把語言檢查定位為提示，不宣稱完整語言校對。

## 建議執行順序與驗收條件

### 第一階段：字幕流程止血

工作項目：分離摘要與警告、輸出前驗證、逐字時間切分、可重複切分、同講者合併、第一張卡處理、語意斷句共用、時間戳備份、SRT 與 speakers 一致性寫入。

驗收條件：

- 目前分支新增的 2 個測試失敗修正，且相較基準分支不增加失敗。
- 任何驗證錯誤都不改寫原始 SRT。
- 超長輸入經處理後，不再留下可由規則判定的超長或過快卡；無法修復時明確列出卡號。
- 不同講者不會因接尾詞規則被合併。
- SRT 卡號與 speakers 映射完全一致。
- 至少加入第一張短卡、跨講者、重疊、超長三次切分、無逐字資料與逐字資料切分測試。

### 第二階段：儲存與工作隔離

工作項目：統一所有儲存入口、加入集數識別與版本號、修正 409 後復原、加入工作識別與集數識別、處理切換集數時的背景工作顯示。

驗收條件：

- 模擬兩個分頁開不同集數時，任何過期請求只得到衝突，不會寫入錯集。
- 所有 `/api/save` 使用同一套衝突處理。
- 409 後重新開集成功才允許重試；重新開集或重試失敗時保留原始錯誤。
- 舊集數工作完成時，新集數畫面不會顯示舊集數結果。
- 轉錄完成、失敗、取消、逾時都能依 `job_id` 對應到正確集數。

### 第三階段：執行環境與發布

工作項目：處理 `audioop` 相容性、擴充 CI、建立 Breeze 資產清單、補建置前檢查、修正髒工作樹判斷、統一版本號與 README。

驗收條件：

- 在支援的每個 Python 版本完成安裝、匯入與測試。
- 沒有 Breeze 模型時，建置能在前置檢查階段給出清楚缺件訊息，而不是中途失敗。
- 髒工作樹或未追蹤程式碼不能產生看似乾淨的發布版本。
- 從乾淨 Git clone 加上指定資產版本，可以產生可驗證的 App。
- App、套件、API 與文件顯示同一版本。

### 第四階段：模組化與測試提升

工作項目：抽出前端 API 與狀態模組、加入 Node 或 Playwright 行為測試、把字幕規則集中到設定物件、補充回歸樣本集。

驗收條件：

- 409、切換集數、轉錄輪詢、潤飾報告都有非文字比對測試。
- 測試可在沒有大型 Breeze 模型的環境執行。
- 前端拆分每一步都能由原有測試與新測試保護，避免一次重寫造成回歸。
- 至少保留一批人工確認過的 SRT，作為時間戳與講者映射的回歸樣本。
